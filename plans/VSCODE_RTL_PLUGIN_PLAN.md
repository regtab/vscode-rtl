## 1. Цель и требования

Универсальное расширение VS Code для разработки RTL-паттернов (Regular Table Language),
**независимое от реализации** RegTab (jRegTab, pyRegTab, будущие порты):

1. Полная редакторская поддержка `.rtl`-файлов: подсветка, скобки, комментарии, сниппеты.
2. Подсветка RTL внутри строковых литералов хост-языков: Python
   (`RtlCompiler.compile("…")`) и Java (`RtlCompiler.compile("…")`, `@RtlSource("…")`).
3. Диагностика ошибок компиляции **без установленного jRegTab/pyRegTab у пользователя** —
   через автономный LSP-сервер `rtl-lsp` (нативный бинарь из Rust-ядра pyregtab).
4. Языковые фичи: hover-справка по токенам, автодополнение, навигация по `$fragment`.
5. Живое превью: матчинг паттерна на таблице-фикстуре с раскраской ячеек и показом
   извлечённого recordset.
6. **Отдельные `.rtl`-файлы — самостоятельный, полностью поддерживаемый сценарий**,
   равноправный со встраиванием RTL в Python/Java-код: паттерны, живущие отдельными
   файлами в произвольной структуре проекта, получают весь набор возможностей без
   хост-рантайма — редактирование, диагностику, превью с настраиваемой привязкой
   файлов данных и проверкой результата против ожидаемого (§5.5). Пример такого
   использования — каталоги решений вида `solutions/regtab/task_NNN.rtl` с таблицами
   в `fixtures/task_NNN/`.
7. Публикация в VS Code Marketplace (publisher `regtab`) и Open VSX.

**Не-цели (в этом плане):** поддержка редакторов, отличных от VS Code-семейства
(PyCharm покрывается TextMate-bundle — та же папка грамматик); диагностика RTL внутри
строк хост-языков (фаза-бэклог, §5.6); стилевой форматтер, сохраняющий авторскую
разбивку.

## 3. Архитектура

Четыре слоя, каждый работает без последующих (деградация — постепенная):

```
┌────────────────────────────────────────────────────────────┐
│ 1. Декларативный слой (без кода, работает везде)           │
│    tmLanguage (.rtl + инъекции Python/Java),               │
│    language-configuration, snippets                        │
├────────────────────────────────────────────────────────────┤
│ 2. TS-клиент (client/):  activation, поиск/запуск сервера, │
│    настройки, команды, webview-превью                      │
├────────────────────────────────────────────────────────────┤
│ 3. rtl-lsp (server/): нативный бинарь, Rust + tower-lsp,   │
│    компилятор из ядра pyregtab; diagnostics, hover,        │
│    completion, definition/rename, symbols, formatting      │
├────────────────────────────────────────────────────────────┤
│ 4. Превью: custom-запросы rtl/matchFixture к rtl-lsp,      │
│    рендер таблицы + recordset в webview                    │
└────────────────────────────────────────────────────────────┘
```

### 3.1 Ключевое решение: LSP-сервер — автономный Rust-бинарь

Обоснование (против альтернатив «Python-сервер поверх pyregtab» и «Java-сервер поверх
jregtab»): универсальность требует, чтобы Java-разработчик получал диагностику, не
устанавливая Python, и наоборот. Rust-ядро pyregtab — полный компилятор RTL, паритет
с jRegTab 0.4.1 зафиксирован conformance-корпусом, значит одна диагностика корректна
для всех реализаций. Бинарь вкладывается в платформо-специфичные VSIX (штатный механизм
Marketplace, по образцу rust-analyzer).

### 3.2 Доработки в pyregtab, необходимые для rtl-lsp

Ядро сейчас не отделено от Python: pyo3 используется не только в `py.rs`, но и в
`interp.rs`, `spec.rs`, `syntax.rs`, `util.rs` (колбэки кастомных предикатов и
`Bindings`). Требуются изменения **в репозитории pyregtab** (отдельный PR, пререквизит
фазы 2):

1. **Cargo-фича `python`** (включена по умолчанию для maturin-сборки): все
   pyo3-зависимые места (`CellPredicate::Custom`, `Bindings`-колбэки, `py.rs`) — под
   `#[cfg(feature = "python")]`. Цель: `cargo build --no-default-features` собирает
   чистое ядро. Проверка в CI pyregtab.
2. **Пермиссивный режим компиляции** — `compile_permissive(rtl)`: любое имя
   `EXT('…')` считается связанным (заглушка «всегда true»). Без этого валидные
   `.rtl` с `EXT` дают ложные ошибки при standalone-редактировании.
3. **Диапазоны ошибок**: `RtlErr` несёт точку (line, col); для качественных
   подчёркиваний желателен span (начало+конец токена). Минимум — длина текущего
   токена из лексера. Некритично для MVP (диагностика «от точки до конца токена/1 символ»).
4. (Попутно, для Python-пользователей) — атрибуты `.line`/`.col` на `RtlCompileError`
   в `py.rs`; расширению не нужно, но напрашивается тем же PR.
5. **Span'ы cell-derived items** (пререквизит уточнённого превью фазы 4, добавлено
   2026-07-12): `CellItem` несёт `span` — байтовый диапазон сегмента в исходном
   тексте ячейки. Матчер уже вычисляет эти смещения при разборе compound-контента
   (`pos`/`end_pos` в `process_compound`) и границы частей delimited-контента, но
   выбрасывает их; изменение лишь сохраняет вычисленное (atomic — весь текст,
   delimited — часть с поправкой на trim, compound — сегмент). Семантика матчинга
   не меняется; поле зеркалируется в `PyCellDerivedItem`.

Способ потребления ядра: `rtl-lsp` живёт в **этом** репозитории (`server/`), зависит от
крейта `pyregtab` через git-зависимость с тегом
(`pyregtab = { git = "…/pyregtab", tag = "v0.4.0", default-features = false }`).
Публикация ядра на crates.io — опционально позже (§9).

### 3.3 Fallback без сервера

Универсальный (platform-neutral) VSIX собирается **без** бинаря: только декларативный
слой. Клиент при активации проверяет наличие бинаря; нет — работает подсветка, в
статус-баре подсказка. Настройка `rtl.server.path` позволяет указать свой бинарь
(например, собранный из исходников на экзотической платформе).

## 5. Фазы реализации

### Фаза 0 — перенос и публикация подсветки (релиз 0.1.x; ~1 день)

Цель: существующая функциональность доступна установкой из Marketplace.

1. Скелет репозитория: `package.json`, лицензия, `.gitignore`, `CHANGELOG.md`.
2. Перенос из `pyregtab/ide/vscode/`: обе грамматики, `language-configuration.json`;
   поля `repository`/`homepage` → этот репозиторий.
3. Java-инъекционная грамматика (`rtl-java-injection.tmLanguage.json`): взять из
   jregtab, если есть; иначе написать по образцу Python-инъекции — триггеры
   `RtlCompiler.compile(` и `@RtlSource(` в `source.java`, однострочные и текстовые
   блоки Java 15+ (`"""…"""`).
4. Marketplace-атрибуты: `README.md` (описание = страница расширения; скриншот
   подсветки), `icon.png`, `keywords` — «Regular Table Language», «RegTab», «table
   extraction», «data wrangling», «DSL» (запрос «RTL» в маркетплейсе занят
   right-to-left-расширениями — находимость строится на полных словах).
5. Регистрация publisher `regtab` (Azure DevOps + PAT), публикация:
   `vsce publish` + `ovsx publish`.
6. `pyregtab/ide/` → README-указатель сюда, файлы грамматик удалить (PR в pyregtab).

**Критерии приёмки:** расширение ставится из Marketplace и Open VSX; `.rtl`-файлы
корпуса подсвечиваются; RTL внутри Python- и Java-строк подсвечивается; универсальный
VSIX < 200 КБ.

### Фаза 1 — сниппеты, тесты грамматики, sync-check (0.1.x; ~1–2 дня)

1. `snippets/rtl.json` по разделу «Frequently used combinations» справочника:
   `ST*->REC`, `(SC{n}, SR)->REC(n)`, `^COL->AVP`, `('LABEL')->AVP`, `CL->JOIN(0)`,
   `-AV->PREFIX(', ')`, каркасы `[ [VAL] [VAL : …]+ ]+`, объявление `$FRAG=[…]`,
   настройки `<NORM, ANCH(n)>`, условная ячейка `[cond ? _ | VAL]`.
2. Снапшот-тесты грамматики (`vscode-tmgrammar-test`) на выборке из
   `pyregtab/conformance/positive/*.rtl` (файлы копируются в `test/grammar/fixtures/`
   со ссылкой на версию корпуса).
3. Порт `check_grammar_sync.py`: перечень токенов-кейвордов из `RTL.g4` совпадает с
   покрытием tmLanguage; job в `ci.yml`.
4. CI: сборка VSIX артефактом на каждый PR.

**Критерии приёмки:** CI зелёный; снапшоты фиксируют текущую токенизацию; рассинхрон
tmLanguage с RTL.g4 валит CI.

### Фаза 2 — rtl-lsp MVP: диагностика (релиз 0.2.x; ~1–2 недели, включая PR в pyregtab)

Пререквизит — PR в pyregtab (§3.2, пп. 1–3).

1. Крейт `server/`: tower-lsp; `initialize`, `didOpen`/`didChange` (full sync — файлы
   маленькие) → `compile_permissive` → `publishDiagnostics` (пусто при успехе; иначе
   одна диагностика с `line:col` и сообщением компилятора). Debounce ~150 мс.
2. Клиент: `vscode-languageclient`, определение платформы → путь к бинарю в
   `bin/`; настройки `rtl.server.path` (переопределение), `rtl.trace.server`.
3. Сборка: `release.yml` — matrix `cargo build --release` под таргеты
   `win32-x64`, `win32-arm64`, `linux-x64`, `linux-arm64`, `alpine-x64`,
   `darwin-x64`, `darwin-arm64`; `vsce publish --target <t>` на каждый + один
   универсальный VSIX без бинаря (fallback §3.3).
4. Тесты: unit в `server/` — весь позитивный корпус компилируется без диагностик
   (в пермиссивном режиме); каждый негативный кейс даёт диагностику с ожидаемой
   позицией; e2e-смоук через `@vscode/test-electron`.

**Критерии приёмки:** опечатка в `.rtl` подчёркивается в редакторе с сообщением
компилятора; позитивный корпус — ноль диагностик; расширение работает на чистой
машине без Python/JDK.

### Фаза 3 — языковые фичи (релиз 0.3.x; ~1–2 недели)

1. **Hover** — справка по токену под курсором: словарь генерируется из таблиц
   `docs/rtl-reference.md` (скрипт в `tools/`, результат — `server/src/hover_data.rs`
   через `include!`/codegen; при изменении справочника регенерация в PR).
   Покрыть: пространственные/позиционные/контентные ограничения, операции,
   экстракторы, настройки, `EXT`, кванторы.
2. **Completion** — контекстно: после `->` — операции; после `=` в contSpec —
   экстракторы; после `#` — известные в документе теги; после `$` — объявленные
   фрагменты; после `<` — настройки; в позиции провайдера — пространственные токены.
3. **Навигация по `$fragment`**: definition, references, rename, documentSymbol
   (фрагменты + структура subtable/row). Требует позиций узлов в AST — если парсер
   их не сохраняет, добавить (тем же PR в pyregtab или локальной обвязкой).
4. **Semantic tokens** (уточнение поверх TextMate: например, различать `ROW` как
   провайдер и как часть контекста) — по остаточному принципу. *Уточнение
   2026-07-17: отложено до фазы 5 шага 1 — честные semantic tokens требуют
   позиций узлов AST (PR в pyregtab), которые понадобятся там же; виртуальные
   документы дадут им вторую причину существовать (подсветка в литералах).*
5. **Канонизация** — РЕШЕНИЕ ИЗМЕНЕНО (2026-07-17, реализовано в 0.6.0):
   не форматтер с настройкой `rtl.format.canonicalize`, а **read-only-команда
   «RTL: Show Canonical Form»** (кастомный запрос `rtl/canonicalize`:
   `compile_permissive → AtpToRtlSerializer.serialize`), открывающая результат
   в отдельном нередактируемом документе рядом. Причины: (а) сериализация
   теряет комментарии, включая директиву `// fixture:` — форматтер молча
   отвязал бы паттерн от фикстуры превью; (б) read-only-вид устраняет риск
   «канонизация уничтожила авторскую разбивку» как класс. Семантика прежняя:
   это нормализация (наследуемые действия опускаются на уровень атомов),
   вывод эквивалентен `.expected.rtl` корпуса. Работает и на `.rtl`-файлах,
   и на литералах Python/Java (механизм извлечения фазы 5 шага 0).

**Критерии приёмки:** hover на каждом кейворде грамматики; completion не предлагает
операции в позиции провайдера и наоборот; rename `$V` меняет объявление и все ссылки.

### Фаза 4 — живое превью матчинга (релиз 0.4.x; ~2 недели)

Киллер-фича: отладка паттерна на реальной таблице.

1. **Ассоциация файла данных** — три механизма, от частного к общему:
   - директива-комментарий в `.rtl`: `// fixture: tables/example.csv`;
   - команда «RTL: Select fixture…» (запоминается в workspaceState);
   - настройка-шаблон на workspace: `rtl.fixtures.input` — glob-шаблон с подстановкой
     переменных, чтобы каталог `.rtl`-файлов с общей конвенцией раскладки данных
     работал без разметки каждого файла. **Механизм не содержит предопределённых
     имён каталогов** — весь путь задаёт пользователь; переменные:
     `${basename}` (имя `.rtl`-файла без расширения), `${dir}` (его каталог),
     `${workspaceFolder}`. Примеры: `${dir}/${basename}.csv` (таблица рядом с
     паттерном), `../../fixtures/${basename}/input_*.csv` (раскладка бенчмарка).
     Значение — строка или **массив правил** `{ "pattern": "<glob для .rtl>",
     "input": "<шаблон>" }` для проектов с несколькими разными раскладками;
     применяется первое правило, чей `pattern` совпал с путём открытого файла.
     Несколько найденных входов на паттерн — переключатель в превью.
2. **Кастомный LSP-запрос** `rtl/matchFixture { patternUri, fixturePath }` →
   `{ table, cells: [{row, col, index, role, s, span}], schema, records, matched,
   error? }`. Гранулярность — **cell-derived item, не ячейка** (уточнено
   2026-07-12): в одной ячейке может быть несколько айтемов с разными ролями
   (компаунд `[VAL ' ' VAL]`, delimited `(VAL){','}`, смешанные `[ATTR ":" VAL]`);
   `role` — роль айтема (value/attribute/auxiliary), `s` — извлечённая строка,
   `span` — диапазон сегмента в исходном тексте ячейки (в символах; из §3.2 п. 5).
   В `rtl-lsp`: чтение CSV (crate `csv`) → построение `TableSyntax` → `AtpMatcher` →
   `TableInterpreter` → сериализация результата. Excel (`calamine`) — второй шаг.
3. **Webview** (`client/src/preview.ts`): рендер таблицы с исходным текстом ячеек,
   внутри которого **диапазоны айтемов** подсвечены цветом роли (VAL/ATTR/AUX);
   текст вне диапазонов (разделители, несматченное) — приглушён; тултип диапазона —
   извлечённая строка `s` (важно при экстракторах `REPL`/`SUBSTR`) и теги. Контекстные
   айтемы (`'…'->AVP`) к ячейкам не привязаны и в раскраске не участвуют. Рядом —
   извлечённый recordset; автообновление при правке `.rtl` (debounce); ошибки
   матчинга — в панель.
4. **CodeLens** над первой строкой `.rtl`: «▶ Preview with <fixture>» / «Select fixture…».
5. **Проверка против ожидаемого результата** (опционально в этой фазе, иначе 0.4.x+1):
   настройка `rtl.fixtures.expected` (glob-шаблон, симметричный `input`); превью
   показывает diff извлечённого recordset против ожидаемого CSV (совпадение/лишние/
   недостающие записи). Опции сравнения (наличие заголовка и т.п.) — настройками.
6. **Test Explorer** (бэклог за фазой): каждая пара `.rtl` × input с наличным expected —
   тест-элемент VS Code Testing API; «запустить все» по каталогу паттернов с
   отчётом pass/fail.

**Критерии приёмки:** правка паттерна мгновенно перекрашивает таблицу и обновляет
recordset; каталог `.rtl`-файлов с конвенцией раскладки настраивается одним
glob-шаблоном на workspace, без правки самих файлов; пример из Task 01 корпуса
работает end-to-end как демо в README (GIF).

### Фаза 5 — RTL внутри строк Python/Java

**Шаг 0 — превью из строковых литералов** (релиз 0.5.0; добавлено 2026-07-12).
Команда/CodeLens «▶ Preview RTL…» на литералах `RtlCompiler.compile(…)`,
`@RtlSource(…)` и `/* language=RTL */ "…"` в Python/Java-файлах. Клиент извлекает
текст литерала (те же триггеры, что в инъекционных грамматиках): Python raw/тройные
строки и Java text blocks — почти дословно (у text blocks снимается incidental
indentation), для остальных — минимальный unescape распространённых
последовательностей. `rtl/matchFixture` получает опциональный `patternText`
(вместо чтения документа по `patternUri`). Ассоциация фикстур переносится как есть:
директива `// fixture:` работает внутри литерала (валидный RTL-комментарий),
запомненный выбор ключуется хост-файлом и позицией литерала, `rtl.fixtures.input`
подставляет `${basename}` хост-файла. Обратный маппинг позиций не нужен (результат
идёт в панель, не в редактор) — шаг обкатывает извлечение литералов до диагностики.
Ограничения (те же, что у инъекций): открывающая кавычка на строке триггера;
конкатенации и f-строки — вне охвата.

**Шаг 1 — диагностика (бэклог).** Виртуальные документы: извлечённый литерал (механизм
шага 0) публикуется как виртуальный `.rtl`-документ, диагностики маппятся обратно в
координаты хост-файла. Подсветка уже есть с фазы 0. Делать после обкатки шага 0.

## 9. Открытые вопросы

1. **Публикация ядра на crates.io** (`regtab-core`)? Пока git-зависимость с тегом
   достаточна; crates.io имеет смысл при появлении сторонних потребителей ядра.
2. **Excel в превью**: MVP — CSV; `calamine` добавить, когда превью докажет ценность
   (стили ячеек — шрифты/выравнивание — в CSV отсутствуют, а `TableSyntax` их
   поддерживает; для паттернов, чувствительных к стилям, Excel станет обязательным).
3. **Идентификатор расширения** — РЕШЕНО (2026-07-11, до публикации): короткий
   `regtab.rtl`, displayName «RegTab RTL». Унаследованный `rtl-language` отвергнут
   как тавтология («Regular Table Language language»); паттерн — `golang.go`,
   `rust-lang.rust`, `Prisma.prisma`. Менять id после публикации нельзя.
4. **Где вести issue по языковым фичам** — здесь или в pyregtab? Рекомендация:
   всё редакторское — здесь; компиляторное (span ошибок, пермиссивный режим) — в pyregtab.
